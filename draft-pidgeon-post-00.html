Post: Signed, Verifiable Identity for Software Agents That Send Email

Abstract

Software agents now send email, and a recipient has no reliable way to tell that a message was written by software, on whose behalf it was sent, or whether the domain it claims to come from stands behind it. This document specifies Post, version 0: an agent declaration carried in ordinary mail and authenticated by an aligned DKIM signature; a per-domain Ed25519 key discovered through DNS and HTTPS; a signed copy of the message in a header field, which a receiver verifies against that key; typed, structured data carried beside the human text; and the format of signed receipts; and a signed card per agent address. Everything specified here, except the signed receipt, is implemented and running in production; the rest is listed as future work.¶

1. Introduction

An email message written by a software agent looks like any other. A recipient, human or software, cannot tell from the message whether a person or a program wrote it, who is responsible for the program, or whether the claims in the message are the sending domain's or a forger's. DKIM [RFC6376] and DMARC [RFC9989] say that a domain handled a message; they say nothing about what kind of sender wrote it or for whom.¶

Two individual drafts propose header fields for part of this: "Agent Attribution Header Fields" [I-D.chuang-agent-attribution-header-fields] defines Agent-of and Agent-attribution, and the "AI Content Disclosure Header" [I-D.abaris-aicdh] defines AI-Disclosure for HTTP. Work on agent identity in the WIMSE working group ([I-D.ietf-wimse-arch], [I-D.ietf-wimse-aims]) addresses workloads that call each other over HTTP, not mail.¶

Post builds on the first two and adds what a recipient needs to rely on them:¶

  1. An agent declaration, using those fields, that a sender emits and a receiver may trust only under a passing, aligned DKIM signature (Section 2).¶
  2. A signing key per domain, discovered from DNS and HTTPS in the manner of MTA-STS [RFC8461] (Section 3), and a signed card per agent address (Section 3.5).¶
  3. A verification procedure with defined outcomes (Section 5).¶
  4. Between two endpoints that both implement Post: a signed copy of the message (the "envelope"), carried in a header field, which binds the declared sender to the From address, the recipients, the text, any structured data and every attachment (Section 6.2); typed data; and receipts (Section 6).¶

Nothing here asks a recipient to change mail software. A receiver that implements none of it sees ordinary mail.¶

1.1. Scope of Version 0

This version specifies only what is implemented, plus the receipt format. In particular, it does not specify delivery over HTTPS between hosts, first-contact policy, end-to-end encryption or a client protocol; see Appendix A.¶

1.2. Conventions and Terminology

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.¶

Agent:
Software that writes and sends messages, typically driven by a language model, on behalf of a person or an organisation.¶
Sender kind:
One of "person", "agent" or "service" (software that is not an agent, such as a workflow or an application). No other value is defined.¶
On behalf of:
A display string naming the party responsible for the sender, such as an organisation's name or its domain.¶
Signing domain:
A domain that publishes a Post policy with at least one key (Section 3) and signs envelopes for its addresses.¶
Host:
The operator of a signing domain's mail service. A host may serve many domains.¶
Receiver:
Any party that checks a message: a receiving mail system, a mail client, or the agent that reads the message.¶
Endpoint:
A sender or receiver that implements this document.¶

base64url is [RFC4648] Section 5 without padding. base64 is [RFC4648] Section 4. Times are [RFC3339] in UTC with a "Z" and no fractional seconds, unless stated otherwise.¶

2. The Agent Declaration

The agent declaration states, in ordinary header fields, that software wrote the message, what kind of software, and on whose behalf. It is readable by any receiver that understands the fields and requires nothing else of the receiving system.¶

2.1. Fields

A sender whose kind is "agent" or "service" emits all three of the following. A person sending a message an agent drafted (for example after approving it) emits only AI-Disclosure. A person sending their own message emits none of them.¶

Agent-of:

As defined in [I-D.chuang-agent-attribution-header-fields]: an address-list [RFC5322] naming who is responsible. A Post sender writes exactly one address. The address SHOULD be an alias at the DKIM signing domain that reaches the responsible party rather than a person's own mailbox, so the field does not publish a personal address. Its display name, when present, is the "on behalf of" value.¶

Agent-attribution:

As defined in [I-D.chuang-agent-attribution-header-fields]: base64 of a JSON [RFC8259] object. That draft leaves the object's members to a future registry. Post defines these:¶

v
The integer 1.¶
kind
The sender kind, "agent" or "service".¶
on_behalf_of
A string, or null when the sender declares no responsible party beyond the Agent-of address.¶
platform
The host's domain name.¶
verify
OPTIONAL. An HTTPS URL at which the host describes this message (Section 2.3).¶
card
OPTIONAL. The URL of the sending address's agent card (Section 3.5).¶

A receiver MUST ignore members it does not recognise.¶

AI-Disclosure:

The field of [I-D.abaris-aicdh], a Structured Field Dictionary [RFC9651], used here in mail with the same syntax. That draft defines the field for HTTP only; this document defines its use in a message header. Values a Post sender writes:¶

  • mode=ai-originated: kind "agent".¶
  • mode=machine-generated: kind "service".¶
  • mode=ai-originated, reviewed-by="person": a person sent what an agent drafted.¶

The kind declared is the kind of what sent the message, not of the address. Software sending from an address that belongs to a person MUST declare "agent" (or "service"), never "person"; "person" means a person composed or approved the message.¶

A host MUST remove any of these three fields that a client supplied (for example in SMTP submission [RFC6409]) and emit only its own. Otherwise any user of the host could put a forged declaration under the host's signature.¶

2.2. Authentication by DKIM

The declaration is trustworthy only under a DKIM signature that covers it, from a domain that answers for it. A sender:¶

  • MUST sign the message with DKIM [RFC6376], with an "h=" tag that includes Agent-of, Agent-attribution and AI-Disclosure (whichever are present), From, To, Cc, Subject, MIME-Version and Content-Type;¶
  • MUST use a signing domain ("d=") that is aligned, in the relaxed sense of [RFC9989], with the domain of the Agent-of address, as [I-D.chuang-agent-attribution-header-fields] Section 1.2.1 requires;¶
  • SHOULD NOT rely on signing Message-ID or Date when a relay is known to rewrite them. (The implementation in Section 8 omits both, because its outbound relay replaces the first and rewrites the second; the signature's "t=" tag dates it.)¶

That signature is separate from, and in addition to, any signature aligned with the From domain. A host that sends for many domains can answer for every declaration with one signing domain, its own, and the receiver learns from the alignment who is answering.¶

2.3. The Verify Link

When Agent-attribution carries "verify", the URL MUST be HTTPS, MUST be unguessable (the implementation uses 128 random bits) and SHOULD return a description of the message as the host recorded it: the kind, the on-behalf-of value, the From address and when it was sent. It MUST NOT return the subject, the body or the recipients, because the link travels with every forwarded copy. The page says the host sent a message; it does not say that the copy in hand is unchanged. That is what the signatures are for.¶

2.4. What a Receiver May Trust

A receiver MUST NOT act on Agent-of, Agent-attribution or AI-Disclosure unless Section 5.1 ends in "signed". Given "signed", the receiver may rely on the host aligned with the Agent-of domain having stated the kind and on-behalf-of value. It has not learned that the statement is true: the host answers for it, as a domain answers for mail it signs.¶

3. Domain Keys and the Agent Card

A signing domain publishes Ed25519 public keys that sign envelopes (Section 6.2) and agent cards (Section 3.5), and will sign receipts (Section 6.4). The pattern is MTA-STS's [RFC8461]: a DNS record says the domain takes part, and an HTTPS document on a dedicated host name holds the policy.¶

3.1. The DNS Record

A TXT record at _post.<domain>:¶

post-record = "v=post0" *WSP ";" *WSP "id=" policy-id
policy-id   = 1*(ALPHA / DIGIT)
¶

The record says the domain signs. The id is a hint to refetch. A host that controls the domain's DNS SHOULD set it to the first 16 hexadecimal characters of the SHA-256 of the policy's exact bytes, so that it changes whenever the policy does. A host that does not control the DNS writes a fixed id once; nothing depends on it changing (Section 3.3). A receiver MUST treat a domain with no such record as not signing.¶

3.2. The Policy

The policy is served at https://post.<domain>/.well-known/post.json [RFC8615], never at the apex: the apex is usually somebody else's website, while post.<domain> can point at the host (for example by a CNAME), which then serves the policy and its TLS certificate. It is a JSON object:¶

v
REQUIRED. The string "post0".¶
max_age
OPTIONAL. Seconds a receiver may hold the policy; 86400 if absent.¶
keys

REQUIRED. An array of key objects, each with:¶

kid
An opaque string naming the key, unique within the domain.¶
alg
"Ed25519". A receiver MUST ignore a key with any other value.¶
pub
The 32-byte public key [RFC8032], base64url.¶
not_after
When the key stops being valid. A receiver MUST ignore a key without a parseable value and MUST refuse a signature made with a key past it.¶
identity
OPTIONAL. An object whose member "issuer" is the HTTPS URL of an OpenID Connect issuer for the domain's addresses. Its use is outside this document (Appendix A).¶
endpoint, first_contact, features
Reserved for delivery over HTTPS (Appendix A). A version 0 receiver MUST ignore them, and a host MUST NOT list in "features" anything it does not implement.¶

A receiver MUST ignore members it does not recognise. A receiver fetching a policy SHOULD use port 443 only, SHOULD NOT follow redirects, SHOULD refuse a host name that resolves to a private or loopback address, and SHOULD refuse a policy larger than 64 KiB.¶

3.3. Caching, Rotation and Refetching

A receiver clamps the policy's max_age to between 60 seconds and 7 days. It fetches the policy again in exactly these cases, checked in this order:¶

  1. It holds no policy for the domain.¶
  2. Its copy is at least max_age seconds old.¶
  3. The TXT record's id differs from the one it saw when it fetched.¶
  4. A signature names a kid its copy does not hold, and its copy is at least 60 seconds old. A receiver MUST NOT refetch for an unknown kid more than once a minute per domain, and MUST refuse a kid still unknown after that.¶

Otherwise it verifies against the copy it holds. This rule is the discovery::decide function of the reference core (Section 8).¶

To rotate, a host publishes the new key beside the old one, signs with the new one at once, and sets the old key's not_after to max_age from now, after which it leaves the policy. A receiver holding the old policy meets an unknown kid and refetches. The TXT id is not needed for rotation, which is why a fixed id works for domains whose DNS the host does not hold.¶

3.4. Signatures

Every Post signature is pure Ed25519 [RFC8032] over the exact bytes being signed. There is no canonical form: the bytes are produced once, signed, and carried and stored as they are; a receiver verifies the bytes it decodes. Two JSON texts equal as JSON but different as bytes do not share a signature.¶

Verification is strict. A receiver MUST reject a signature whose S is not less than the group order L, and MUST reject a public key or an R that is a point of small order. Plain verification as in [RFC8032] accepts some such signatures; the test vectors in Appendix C pin the line.¶

3.5. The Agent Card

The card is the newest part of this document (implemented 3 November 2026) and the most likely to change. Nothing in Section 5 depends on it.¶

The declaration and the envelope give identity per message. The card gives it per address: a document, issued automatically by the address's host, that says what the address is and that a holder can check offline against the issuer's policy.¶

3.5.1. Format and Signature

A card is a JSON Web Signature [RFC7515] in compact serialisation, with protected header {"alg": "EdDSA", "typ": "agent-card+jwt", "kid": <kid>}. The kid names a key in the issuer's policy (Section 3.2), and the signature is Ed25519 over the JWS signing input, verified strictly (Section 3.4). The typ keeps a card from being mistaken for another token signed by the same key. The payload is a JSON object:¶

iss
https://post.<issuer domain>: the address's own domain when it signs, else the host's domain.¶
sub
A stable identifier for the address that the issuer never reassigns, even if the address is deleted and created again.¶
iat, exp
Issued and expiry times, in seconds since the epoch. The implementation issues cards valid for a day and signs one afresh on each fetch.¶
v
"post0".¶
address
The address.¶
kind
"agent" or "service". Never "person": a card says software speaks from the address. An address only people have sent from has no card, and a request for one is answered as for an address that does not exist. An address that software has sent from, declaring "agent", has a card of kind "agent" from its first such message on, so the card a message names can always be fetched.¶
on_behalf_of
As in the declaration; omitted when there is nothing to say.¶
operator
{"domain", "verified"}: the account's domain and whether the host has verified control of it; omitted when there is none.¶
created_at
When the address was created.¶
keys
What signs the address's mail, so a receiver knows what to expect: {"type": "post", "domain", "kid"} for the envelope key and {"type": "dkim", "domain", "selector"} for the signature over the declaration.¶
reputation
Coarse, never a count: "standing" is "new" (an address under 30 days old), "established" or "restricted" (suspended), and "since" is a month (YYYY-MM).¶
url
The card's permanent URL.¶

A card carries only what the address's own mail already says, or facts about its domain: never an owner, a member, or anything a mailbox holds.¶

3.5.2. Discovery and Checking

  • From the mail: the Agent-attribution object carries a member "card", the card's URL, beside "verify" (the message's own page). It is under the declaration's DKIM signature.¶
  • From the address alone: GET https://post.<domain>/.well-known/post/card?address=<address> returns {"object": "agent_card", "url", "jws", "card"}, where card is the payload decoded for reading and jws is the authority.¶

To check a card, a receiver takes the domain from iss (the host name without its leading "post." label), obtains that domain's policy and the key named by kid (Section 3.3), verifies the signature, checks exp, and checks that address is the address it is asking about. A card from an issuer other than the address's own domain is the host's statement, not the domain owner's.¶

The address lookup lets anyone ask whether an address is an agent's. SMTP already says whether it exists and its mail says the rest; the implementation rate-limits the lookup per client address.¶

3.5.3. Revocation

An issuer revokes a card by withdrawing it: from then on a request for the card, by its URL or by address, is answered as for an address that does not exist (HTTP 404), and the card log records a "revoked" entry for its sub (Section 3.5.7). Revocation cannot be undone, and an issuer MUST NOT reuse a revoked card's sub. A host issuing for accounts (Section 3.5.1) MUST NOT issue a card for a revoked card's address again, to anybody: a receiver that trusted the address would otherwise extend that trust to whoever holds it next. A domain issuing for its own addresses (Section 3.5.4) SHOULD NOT; if it does, the card has a new sub and the log a new subject, so a receiver keyed on sub sees a stranger.¶

A receiver holding a copy may believe it until its exp, at most a day in the implementation. A receiver acting on a card for something that matters SHOULD fetch it afresh or check the log's head, rather than rely on a copy. Suspending an address is not revocation: its card stays, with reputation standing "restricted".¶

3.5.4. Issuance for a Domain the Host Does Not Hold

A host can issue cards for addresses on any domain, with no account, in the way ACME's DNS challenge [RFC8555] issues certificates. The operator of the domain holds the signing key; the host holds only its public half and signs the cards.¶

  1. The operator makes an Ed25519 key. Its key id, wherever this document uses one for it (the policy's kid, the envelope's k, an HTTP signature's keyid), is its JWK thumbprint [RFC8037], base64url-encoded.¶
  2. The operator claims the domain at the host, naming the public key, in a request signed by that key (Section 3.5.5, with the tag "pidgeon-id"). The host answers with the record that proves the claim: the domain's post TXT record (Section 3.1) with an id that is the first 16 hexadecimal digits of SHA-256 over the UTF-8 string "post id claim", a NUL, the domain, a NUL and the key id.¶
  3. Once that record is published, the domain is the key's. A claim made by anyone else, before or after, names another key and so another id, and never proves. Proving the domain again with a new key replaces the old key and every card issued under it.¶
  4. The operator registers addresses at the domain, in requests signed by the domain's key. Each gets a card (Section 3.5.1) whose iss is the host's domain, whose operator is the proved domain with verified true, and whose keys name the operator's key. The host signs it on each fetch, valid for a day, while the record stands, so a card renews itself and lapses when the record is removed.¶
  5. The host serves the domain's policy, from the operator's public keys, at https://post.<domain> once the operator points that name at it. The policy carries no endpoint.¶

The operator's key signs the address's envelopes (Section 6.2) and HTTP requests (Section 3.5.5). A receiver verifies them against the domain's policy, as for any domain.¶

3.5.5. Agent Requests over HTTP

An agent signs an HTTP request with HTTP Message Signatures [RFC9421] in the profile of [I-D.ietf-webbotauth-httpsig-protocol], so that a receiver that checks Web Bot Auth signatures needs nothing new. The implementation signs with alg "ed25519", tag "web-bot-auth", keyid the key's JWK thumbprint, and a validity of five minutes. It covers @method, @authority, @path, @query when there is one, Signature-Agent, From, and Content-Digest [RFC9530] when there is a body.¶

  • Signature-Agent is "https://post.<domain>", sent as a bare String, the form deployed verifiers read today; a receiver also accepts the Dictionary form the profile asks signers for.¶
  • From is the agent's address. A receiver treats it as the sender only when it is at the domain whose key verified the signature.¶
  • The domain's key directory, at https://post.<domain>/.well-known/http-message-signatures-directory, lists the same keys as its policy, as a JWK Set whose kids are their thumbprints. The implementation does not sign the directory response, since the host does not hold the keys.¶

A call to an MCP server over its HTTP transport is an HTTP request, and is signed the same way.¶

Post does not replace Web Bot Auth; it is one more way to find out who holds the key. A Web Bot Auth verifier checks a Post agent's request with nothing new: same profile, same key directory, same keyid. What Post adds sits beside the signature, not in it:¶

  • An address. The covered From names one agent among many under one key, where Web Bot Auth names an operator.¶
  • The agent card (Section 3.5), found from that address: kind (agent or service), on_behalf_of, a verified operator domain, and a coarse standing.¶
  • One key for mail and HTTP. The envelope's k and the request's keyid are the same thumbprint, published in the policy and the key directory alike.¶

A grant (Section 4) rides beside the signature in a Post-Grant field, which the signature covers like From.¶

3.5.6. A Card in an A2A Agent Card

An agent that publishes an A2A Agent Card [A2A] can carry its Post identity in it with A2A's own mechanisms, so that an A2A client needs nothing new and a Post-aware one can check it:¶

  • An entry in capabilities.extensions with uri https://pidgeon.ai/post/a2a/v0, required false, and params address, kind, on_behalf_of (when there is one), operator (the domain), card_url and card_jws (the card's compact JWS, which is the authority; the other members are for reading).¶
  • An entry in signatures (A2A's AgentCardSignature): JWS JSON form without the payload, over the RFC 8785 [RFC8785] canonical form of the Agent Card without signatures, by the operator's key. The protected header has alg "EdDSA", kid the key's JWK thumbprint, and jku the domain's key directory (Section 3.5.5), which is a JWK Set.¶

The fields map as follows: the Post card's address and kind have no A2A counterpart and travel in the extension; operator corresponds to AgentProvider (organization, url), which A2A does not verify and the card does; the A2A card's name, description, skills and interfaces have no Post counterpart. A verifier checks the signature against the key at jku, then the card_jws against its issuer's policy, then that the card's address is at the domain whose key signed the A2A card.¶

A grant (Section 4) is not part of an A2A Agent Card, which is public and names no customer. An A2A client sends it with the task instead: in the message's metadata, under the extension's uri, as {"grants": [<compact JWS>, ...]}.¶

3.5.7. The Card Log

A host that issues cards automatically can issue one for anybody, including a card that names somebody else. The card log makes every card the host issues public, so the impersonated party can find it, in the way Certificate Transparency [RFC9162] makes every certificate public. It is an append-only Merkle tree whose heads the host signs; anyone can check that a card is in it and that the log only ever grew.¶

An entry records a change to a card subject, not a signed card, since cards are re-signed daily (Section 3.5.1). It is a JSON object in its canonical form [RFC8785], and its exact bytes are what the tree hashes:¶

v
"post0-log".¶
event
"issued" (the subject has a card, for the first time or again), "updated" (a logged member below changed), or "revoked" (it has none).¶
time
When the log saw the change [RFC3339], to the second.¶
sub, address
As in the card. Every entry about one address carries the same sub.¶
prev
The index of the subject's previous entry; omitted on its first.¶
iss, kind, on_behalf_of, operator
As in the card; omitted on "revoked".¶
keys
As in the card, except that a "post" key also carries "pub", the public key in base64url, so a key replaced under the same kid is a change the log shows. Omitted on "revoked".¶

The card's iat, exp, reputation, created_at and url are not logged: they change by the day or never.¶

The tree is that of [RFC9162], Section 2.1: a leaf hash is SHA-256 of 0x00 and the entry's bytes, an interior node SHA-256 of 0x01 and its children, and inclusion and consistency proofs are built and verified as Sections 2.1.3 and 2.1.4 say. The signed tree head is a checkpoint [C2SP.checkpoint]: three lines (the log's origin, its size in decimal, its root hash in base64) in a signed note [C2SP.signed-note] with one Ed25519 signature [RFC8032], whose key name is the origin. The log's key is the log's identity and never rotates; a client pins it as a signed-note verifier key.¶

The implementation serves, with no credentials:¶

  • GET /v1/log/head and, as text, GET /v1/log/checkpoint: the current checkpoint and verifier key.¶
  • GET /v1/log/entries?start=&end=: entries by index, each with its exact bytes.¶
  • GET /v1/log/proof?sub= (or index and tree_size): an inclusion proof against a checkpoint.¶
  • GET /v1/log/consistency?first=&second=: a consistency proof between two sizes.¶

A verifier given a card and an inclusion proof hashes the entry's bytes, checks that the entry's sub and claims are the card's, verifies the checkpoint with the pinned key, and verifies the proof against its root. The implementation's verifier returns that proof with its verdict. A monitor keeps the last checkpoint it verified, asks for a consistency proof each time the size grows, and reads the new entries; a card it did not expect, for a name it watches, is the alarm. The log is reconciled from the cards every five minutes, its maximum merge delay. The Card Log vectors are in Appendix D.¶

4. Grants

Grants are newer than the card (implemented 4 November 2026) and the most likely part of this document to change.¶

The card says who an agent is and for whom it acts. A grant says what it may do: that a person or an organisation allowed this agent to act within a named scope, for one customer, account or order, with one recipient, until a time. A recipient that is about to act on an agent's request (a support desk changing a booking, a vendor issuing a refund) checks the grant before it acts.¶

4.1. Format and Signature

A grant is a JWS [RFC7515] in compact serialisation, with protected header {"alg": "EdDSA", "typ": "agent-grant+jwt", "kid": <kid>}, signed and verified as a card is (Section 3.5.1). The typ keeps a grant from being taken for a card or another token signed by the same key. The payload:¶

iss
https://post.<issuer domain>: the host that saw the grantor agree. The implementation signs with the key of the domain that signs the cards it issues itself.¶
jti
The grant's identifier, which the issuer never reuses.¶
sub
The agent's card sub (Section 3.5.1).¶
agent
The agent's address.¶
iat, exp
Issued and expiry times, in seconds since the epoch. The implementation lets the operator cap the term, at most 366 days.¶
v
"post0".¶
grantor
{"type": "person", "email", "confirmed_by"}, where confirmed_by is "email" (the person followed a link the issuer sent to that address) or "session" (they were signed in to the issuer as it); or {"type": "organisation", "domain", "confirmed_by": "domain"}, a domain the issuer has verified, granted by an administrator of the account that holds it.¶
scope
{"name", "label", "limit"?}: name is stable, for software ("bookings.manage"); label is what the grantor was shown ("manage your bookings"); limit is {"amount", "currency"}, an integer in the currency's minor units and an ISO 4217 code. Scopes are the operator's; this document defines none.¶
aud
The domain the agent may act with. Omitted: any.¶
subject
{"type", "id"}: type is "customer", "account" or "order", and id is in the recipient's own terms.¶
status
An https URL at the issuer that answers whether the grant still holds (Section 4.4).¶

4.2. Issuing

The operator of an agent defines the scopes its agents may ask for. The agent asks a person, by email address, for one scope, one subject and a term; the issuer makes a pending request and a consent page, which says, for example, "Acme's assistant wants to manage your bookings with Delta until 31 December 2026". The person answers there. Holding the page's address is not consent, since the operator holds it too: the person allows the grant only after following a link the issuer sends to the address asked, or while signed in to the issuer as that address. Only then does the issuer sign. An organisation grants its own agents directly. Either the grantor or the operator may revoke a grant at any time, and a revoked grant is never restored.¶

4.3. Carrying a Grant

  • In mail: a Post-Grant header field per grant, whose value is the compact JWS. White space in the value is not part of it, so a sender may break the value at any point to fold the field; a receiver removes all white space.¶
  • In HTTP: a Post-Grant field, several grants separated by commas (a JWS contains none), covered by the request's signature (Section 3.5.5).¶
  • In an MCP call: under the key ai.pidgeon.post/grant in the request's _meta, as a compact JWS or a list of them.¶
  • In A2A: in the message's metadata (Section 3.5.6).¶

A receiver reads at most five grants from one message or request.¶

4.4. Checking a Grant

A grant on its own proves nothing about who presents it: it is a bearer statement until it is bound to a signature. A receiver accepts a grant only when all of the following hold, and reports the first that does not:¶

  1. It is a grant: a compact JWS with this typ and every member above ("malformed").¶
  2. Its iss is an issuer the receiver checks grants from ("unknown_issuer"), and the signature verifies under the key kid names in that issuer's policy ("bad_signature").¶
  3. The issuer holds it in force: given, not revoked ("revoked"), and the same grant ("not_found"). A receiver that is not the issuer asks the status URL, which answers {"object": "grant_status", "id", "status", "expires_at", "revoked_at"} with status "active", "revoked" or "expired", and 404 for a grant never given. The implementation's verifier reads its own record on every check, and its status URL is cached for at most thirty seconds, so a revocation is seen within a minute.¶
  4. exp is in the future ("expired").¶
  5. A signature on the same message or request verifies as an address (Section 5, Section 3.5.5) ("sender_unverified"), and that address is the grant's agent, still holding the grant's sub ("wrong_agent").¶
  6. Where the receiver knows where it arrived (the recipient's address, or the request's host), that is aud or under it ("wrong_audience").¶
  7. Where the receiver knows which customer, account or order it is about to act on, that is subject.id ("wrong_subject").¶

A grant never changes the verdict on the sender; it is a separate answer about what the sender may do.¶

5. Verification

A receiver checks the two layers independently. Either may be absent; each has its own outcome.¶

5.1. The Declaration

  1. If the message has none of Agent-of, Agent-attribution and AI-Disclosure, the outcome is "absent".¶
  2. Find DKIM signatures whose "h=" tag covers every instance of those fields that is present, and whose "d=" is aligned (relaxed) with the domain of the Agent-of address. A message with AI-Disclosure alone has no Agent-of to align with: any DKIM signature covering the field qualifies, and its "d=" names the party answering for it. If there is none, the outcome is "absent": the message claims a declaration that nobody answers for, and a receiver SHOULD say so.¶
  3. Verify such a signature [RFC6376]. If none verifies over the header fields, the outcome is "changed".¶
  4. Read the facts only from the field instances the signature covered (in DKIM, the last instances). An instance outside the signature, such as a second Agent-of added in transit, MUST be ignored and SHOULD be reported.¶
  5. If the body hash also verifies, the outcome is "signed", body "intact". If only the header fields were available (for example a pasted header section), it is "signed", body "not checked". If the body hash fails, the declaration is "signed" but the body is "changed", and a receiver MUST NOT treat the body as the sender's.¶

5.2. The Envelope

For a message with a Post-Envelope field, in this order, stopping at the first failure:¶

  1. Parse. Take the field; remove whitespace from each tag value; require v, d, k, s and m, and v equal to "post0". Otherwise: malformed.¶
  2. Domain. d MUST equal, ignoring case, the domain of the From address. Otherwise: domain_mismatch.¶
  3. Key. Obtain d's policy and the key named by k by the rules of Section 3.3. No TXT record: not_published. No usable policy: policy_unavailable. A kid still unknown: unknown_kid. A key past not_after: expired_key.¶
  4. Signature. Decode m and s, and verify s over the bytes of m, strictly (Section 3.4). Otherwise: bad_signature.¶
  5. Message. The bytes of m MUST be valid UTF-8 JSON with v "post0" and a sender.kind that is a sender kind. Otherwise: invalid_message.¶

  6. Agreement with the MIME. The signed message MUST say what the MIME says, because the MIME is what will be shown and stored:¶

    • sender.address equals the From address, ignoring case (sender_mismatch);¶
    • subject equals the decoded Subject (subject_mismatch);¶
    • to and cc, as sets and ignoring case, equal the To and Cc addresses (recipients_mismatch);¶
    • the text part equals the message's text/plain body, after converting CRLF to LF and removing trailing whitespace from both (text_mismatch);¶
    • the data part, if any, equals the typed data in the MIME, and there is typed data in the MIME only if there is a data part (data_mismatch);¶
    • the set of attachment sha256 values equals the set of SHA-256 hashes of the files carried; a file the message does not list fails (attachment_mismatch).¶

If every step passes, the outcome is "pass", and the declared sender is the signed message's sender.kind and sender.on_behalf_of. Anything not checked above, the HTML alternative in particular, is not covered, and a receiver that has a "pass" SHOULD show the text rather than the HTML.¶

Without a Post-Envelope field the outcome is "none".¶

5.3. Combining the Outcomes

  • Envelope "pass": the declared sender is the envelope's. It is the sending domain's own statement, and it is bound to the content.¶
  • Otherwise, declaration "signed": the declared sender is the declaration's, stated by the host aligned with the Agent-of domain.¶
  • Otherwise: no declared sender. The receiver records the kind and on-behalf-of as unknown, not as "person". Mail arriving this way from ordinary email is said to have origin "smtp".¶

A failed envelope is evidence that something is wrong. A receiver MUST NOT treat it as "pass", and MAY refuse the message.¶

"pass" proves that the domain wrote this content for these To and Cc recipients. It does not prove that this copy was sent to this receiver (Section 9.3), and it does not replace DMARC as the test of whether the From domain sent this copy.¶

6. Between Post Endpoints

When both ends implement Post, the same message carries more than either end gets from ordinary mail. Version 0 specifies what an endpoint delivers over ordinary SMTP, or by any equivalent hand-off between two endpoints run by the same host; delivery over HTTPS between hosts is future work.¶

6.1. Knowing the Other End Speaks Post

A sender learns that a recipient's domain signs from the _post record (Section 3.1). Version 0 gives no stronger signal: a domain that signs is not thereby promising to verify. A host may know more about addresses it hosts itself.¶

6.2. The Signed Envelope

A signing domain signs each message it sends as a JSON document, the "message", and carries it with the signature in a header field. A receiver that holds the domain's key can then check the declared sender and the content against the domain's signature, with no DKIM involved and no dependence on how relays rewrite the MIME.¶

6.2.1. The Message

A JSON object, UTF-8, serialised once. Members:¶

v
"post0".¶
id
An opaque string of at most 64 characters, unique per sending domain.¶
thread
An object: "id", set by whoever starts the conversation and never changed; and "parent", the id of the message replied to, when it is a reply.¶
sender
An object: "address", the From address; "kind", the sender kind; and "on_behalf_of", present only when the sender declares one. These are the same values as the agent declaration's (Section 2).¶
to, cc
Arrays of addresses, as in the To and Cc fields. Bcc recipients never appear.¶
created_at
When the message was written.¶
subject
The Subject, decoded.¶
parts

An array, in this order:¶

  • exactly one text part: {"role":"text", "type":"text/plain", "body": <the text>};¶
  • at most one data part: {"role":"data", "schema": <URL>, "body": <any JSON>} (Section 6.2.3);¶
  • one attachment part per file: {"role":"attachment", "type": <media type>, "name": <file name>, "sha256": <hex>, "size": <octets>}.¶

The text part is written for a person. A receiving agent MUST treat it as untrusted content to read, never as instructions. HTML is not part of the message and nothing vouches for it.¶

The message carries files by hash only: at the SMTP border the bytes travel in the MIME beside it.¶

6.2.2. The Post-Envelope Header Field

The field's value is a list of tag=value pairs as in DKIM [RFC6376] Section 3.2:¶

  post-envelope = "Post-Envelope:" FWS env-tags CRLF
  env-tags      = env-tag *( ";" FWS env-tag ) [";"]
  env-tag       = tag-name "=" tag-value   ; RFC 6376, Section 3.2
¶
v
"post0".¶
d
The signing domain. It MUST be the domain of the From address.¶
k
The kid of the key that signed.¶
s
The Ed25519 signature over the message bytes, base64url.¶
m
The message bytes, base64url.¶

A sender breaks the values of s and m into runs (the implementation uses 76 characters) separated by spaces so the field can be folded; a receiver removes all whitespace from every value before using it, as from a DKIM "b=" tag. A receiver MUST ignore tags it does not recognise.¶

A sender SHOULD NOT emit the field when the message is larger than 24 KiB before encoding: some mail systems discard header text past 100 KB, which would leave an envelope that cannot be verified. Such a message goes out without one, as does mail from a domain that does not sign.¶

6.2.3. Typed Data in MIME

A message may carry one piece of structured data beside its text: a "schema", an http or https URL of at most 900 characters naming what the data is (for example https://schema.org/Offer), and a "body", any JSON value of at most 64 KiB serialised. It travels:¶

  • in the envelope, as the data part;¶
  • in the MIME, as an alternative inside the message's multipart/alternative, after any HTML alternative and before any calendar part, with type application/vnd.post+json, parameters charset=utf-8 and schema="<URL>", and base64 transfer encoding.¶

It is an alternative, not an attachment, so a client that does not understand it shows the text or HTML. A receiver lifts the first such part whose content is JSON and whose schema is an http(s) URL into the message's data; anything else stays an attachment.¶

The schema is a label a receiver may check, not something version 0 validates. Data is parsed as data. A receiving agent MUST NOT treat it as instructions, and a screening system that reads prose for prompt injection has no reason to read it.¶

6.3. Delivery

A sender delivers one copy per recipient, carrying the Post-Envelope field, the typed data alternative and the agent declaration. A receiving endpoint runs Section 5.2 before storing anything. On "pass" it stores the copy with the declared sender from the envelope and the text (not the HTML), and reports that the signature passed. On failure it MUST NOT store the copy as verified.¶

A receiver keeps the original bytes of a delivered copy where it can, so the signature can be checked again later.¶

The Message-ID SHOULD be the same on every recipient's copy, so a reply from an ordinary mail client threads back to the conversation.¶

6.4. Receipts

A receipt tells a sender what happened to a message after it reached the recipient's endpoint. Kinds:¶

delivered
The copy is in the recipient's mailbox.¶
read
The receiving agent or person opened it. A recipient MUST NOT send it unless the recipient's mailbox has opted in, and MAY refuse it without saying why. It is off by default.¶
handed_off
The recipient's conversation passed from software to a person.¶
failed
The message could not be delivered.¶

A receiving endpoint sends each kind at most once per received copy.¶

6.4.1. The Receipt

A JSON object, signed as exact bytes like the message:¶

v
"post0".¶
message_id
The id of the message (Section 6.2.1).¶
from_domain
The sending domain. Ids are unique per sending domain only, so the pair names the message.¶
recipient
The address whose copy this is.¶
kind
The receipt kind.¶
at
When it happened.¶

The recipient's domain signs the bytes with a key from its own policy. A sender that keeps the bytes and the signature can show a third party that the recipient's domain confirmed the event.¶

6.4.2. Carrying a Receipt

A receipt travels as a JSON object with members "v" ("post0"), "d" (the recipient's domain), "kid", "receipt" (the receipt bytes, base64url) and "sig" (the signature, base64url). A receiver of a receipt verifies it as in Section 5.2 steps 3 and 4, against d's policy, and checks that recipient's domain is d.¶

How a receipt reaches the sender is outside version 0; between addresses on one host it is an internal event. Over HTTPS between hosts it is future work (Appendix A).¶

8. Implementation Status

This section is to be removed before publication, as [RFC7942] describes.¶

Pidgeon, an email service for people and software agents, implements everything in this document except the signed receipt (receipts are emitted unsigned, in the receipt's shape, as events to the sender). On 3 November 2026 the agent declaration was on 565 of 984 messages sent in the previous 7 days. Every message sent through the API from a signing domain carries Post-Envelope, unless it is over the size limit of Section 6.2.2; messages from a user's own mail client by SMTP submission carry none. Between two Pidgeon addresses on signing domains, copies are delivered directly and verified by Section 5.2 before they are stored; a copy that fails is refused and sent as ordinary mail.¶

The core is "post-core", in Rust (Apache-2.0), with a WebAssembly binding: Ed25519 signing and strict verification, and the refetch rule of Section 3.3. The test vectors in Appendix D are produced from the running code.¶

Pidgeon also runs a public checker for the declaration, which reports the outcomes of Section 5.1 for a pasted message, and of Section 3.5.5 for a signed request. It issues cards for domains it does not host (Section 3.5.4); the operator's side is "@pidgeon-ai/id" (Apache-2.0), a command line and the signing library, over the same post-core.¶

Grants (Section 4) are issued for addresses the implementation hosts, through its consent page, and checked by the same public checker; "@pidgeon-ai/id" carries them in mail and HTTP. It issues none yet for domains it does not host, and does not check grants from other issuers.¶

Known limits of the implementation: its inbound path from ordinary email does not yet verify Post-Envelope fields from other domains (the remote fetch of Section 3.3 exists but is not called there); the DKIM signature over the declaration is the host's (d=pidgeon.email), not a second one from a customer's domain; and no receiver other than Pidgeon is known.¶

9. Security Considerations

9.1. A Signature Is Not a Truth

The declaration and the envelope prove who stated something, not that it is true. A domain that lies about its sender's kind is caught only by the reputation of the domain that signed. Receivers SHOULD treat the signing domain, not the declaration, as the accountable party.¶

9.2. Forged Declarations

Agent-of and its companions are ordinary header fields anybody can write. They are worth nothing without Section 5.1, and a host that signs for many users MUST strip client-written instances (Section 2.1), or its signature would cover a forgery.¶

9.3. Replay

The envelope binds the content and the To and Cc recipients, but Bcc recipients are legitimately absent from it, so a receiver cannot tell a copy sent to it by Bcc from a captured message replayed to it. Version 0 has no freshness on the envelope: created_at is when the message was written, and a message may be retried for days. A receiver SHOULD NOT treat an envelope "pass" alone as proof that the From domain sent this copy to it; DMARC answers that question for mail that arrives by SMTP. The implementation trusts "pass" as sender authentication only for copies handed over directly by its own sending path, and ignores Post-Envelope on mail that arrives over SMTP. Binding a delivery to its recipients and a time is future work (Appendix A).¶

9.4. Key Compromise and Revocation

Revocation is never instant. A stolen key is usable until the host removes it from its policy and every receiver's copy expires, at most the clamped max_age (7 days), and never past the key's not_after. Hosts SHOULD keep max_age short while withdrawing a key. The unknown-kid refetch is rate-limited so that an attacker cannot make a receiver fetch a policy on every message.¶

9.5. Fetching Policies

A policy fetch is a request a sender can make a receiver perform. The limits in Section 3.2 (port 443, no redirects, no private addresses, a size cap) prevent its use against the receiver's own network. A policy is trusted only as far as the TLS certificate for post.<domain> and the domain's DNS are.¶

9.6. Content Written for People, Read by Software

The text part and the HTML are untrusted input. A receiving agent MUST NOT follow instructions found in them, whether or not the envelope passes: a signature says who wrote the text, not that it is safe. Typed data is parsed as data.¶

9.7. Signature Malleability

Strict Ed25519 verification (Section 3.4) ensures one message has one valid signature per key, and that a weak key cannot make a forged signature pass. Implementations that use a library's default verification SHOULD check it against the vectors.¶

10. Privacy Considerations

  • Agent-of names a responsible party. It SHOULD be an alias rather than a person's mailbox. A host SHOULD NOT derive on_behalf_of from a person's name or address unless that person chose to publish it; the implementation uses an organisation name an owner set, else a verified domain, else nothing.¶
  • The verify link travels with every forward. It MUST NOT reveal the subject, body or recipients (Section 2.3).¶
  • The envelope repeats the To and Cc addresses and the text in a header field. It reveals nothing a recipient does not already have, but mail systems that log header fields will log it.¶
  • A read receipt reveals behaviour. It is off by default and opt-in per mailbox.¶
  • A grant names its grantor's email address and a customer, account or order, and travels to the recipient named in aud, who already knows both. The grantor sees that before agreeing. The status URL answers only for a grant that was given, by an identifier only a holder of the grant has, and says nothing of grantor, scope or subject.¶
  • A policy fetch tells the sending domain's host that some receiver is checking its mail, and roughly when. Caching limits this to once per max_age per receiver.¶

Appendix B. Notes for a Second Implementation

A receiver that verifies envelopes needs: an Ed25519 library with strict verification, a DNS TXT lookup, an HTTPS client, a JSON parser and a MIME parser. It does not need a JSON canonicaliser. Points that are easy to get wrong:¶

  • Verify the decoded bytes of m. Never re-serialise the parsed JSON and verify that.¶
  • Remove whitespace from every tag value before decoding: the field is folded.¶
  • base64url without padding for Post-Envelope, the policy's keys and receipts; ordinary base64 for Agent-attribution.¶
  • Compare the signed text with the text/plain body after CRLF to LF and trimming trailing whitespace; compare recipients as case-insensitive sets.¶
  • Refuse S >= L and small-order points. The vectors in Appendix C fail under a lax verifier.¶
  • Rate-limit unknown-kid refetches per domain, across all of your processes.¶

A conformant receiver: verifies every valid vector; refuses every vector marked invalid; on the message in Appendix D reaches "pass" for the envelope given the sender's policy, and "signed" with body "intact" for the declaration given the DKIM record; and reaches domain_mismatch on the refusal vector that changes d.¶

Appendix C. Ed25519 Vectors

The file ed25519.json, published with post-v0.json, holds RFC 8032's Section 7.1 tests 1 to 3, a protocol message and delivery signed with the seed 0x00..0x1f, a UTF-8 vector, and five refusals: the same JSON with a number written differently (1240.50 as 1240.5), a changed message, a wrong key, S + L (non-canonical S), and the identity point as key and R with S = 0 (passes plain RFC 8032 verification for any message).
